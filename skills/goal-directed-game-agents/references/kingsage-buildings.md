# KingsAge building documentation — research recipe

Use this when a KingsAge objective depends on construction costs or unlocks. The public game help has both a building index and individual detail pages; read them before inferring dependencies from a fixture.

1. Open the player's own world's `https://<world>.kingsage.gameforge.com/help.php?m=buildings` and follow each `build=...` link to `help.php?m=buildings&sub=details&build=<slug>`. Public pages may be available before login; use the account's live UI to confirm any action. Start with `main` (Castelo), `storage` (Armazém) and `farm` (Moinho) for a castle goal.
2. Distinguish the optional **Requisitos** section (static requirements to unlock an edifice) from the level table's **Precisas de** columns (cost to build *that* level). An absent prerequisites section means none are *listed on that help page*, not proof that every in-game condition has been satisfied. Do not infer a warehouse dependency for the castle solely because storage could theoretically become a bottleneck.
3. The public help detail tables use image-only resource headings: `res1.png` = madeira, `res2.png` = pedra, `res3.png` = ferro. Inspect the actual icons rather than assuming column order. **Do not carry this mapping over to the live build card's CSS classes `.res1`, `.res2`, `.res3` without inspecting their icons/styles:** the same numbered names in different page components do not prove the same resource order. Rows may use `.` as a thousands separator; parse `1.000` as one thousand, not a decimal. The castle table also lists additional/total workers and a time factor; the warehouse table lists capacity and the mill lists worker capacity.
4. When collecting multiple buildings, enumerate real detail links from the index and verify the heading and level table of each result. A link slug alone does not guarantee that it resolves to a building detail page; retry intermittent responses before declaring data missing. Keep source URLs beside extracted values.
5. Reconcile documented costs against live balances, per-resource storage and free-worker capacity. Fixture values are illustrative only; never silently promote them to game data. For a castle goal, state separately whether the documentation lists a structural prerequisite, whether current resources suffice, and whether workers/storage/queue permit the action.

6. A public `GET https://<world>.kingsage.gameforge.com/game.php?screen=main` can return HTTP 200 **after redirecting to** `lobby.kingsage.gameforge.com`. Check the final host before claiming to have account status; an available help page and an unauthenticated lobby do not reveal resource balances or command routes. For a user-supplied authenticated `curl`, try a read-only `GET /?village=<id>&s=build_main` with only the world-scoped `KingsAge-Game` cookie first; verify no redirect to lobby and confirm account-specific DOM (`#build_main`, `#stone`, `#wood`, `#iron`) before building an observer. Those resource nodes can carry `start` and `max` attributes; read text for current balances and `max` for capacity, rather than treating an unlabeled header number as capacity. Parse `.mainBuildList .box` for building names, levels, costs, workers and time, but confirm its numbered resource classes against live icons/styles. The authenticated page uses server-rendered links, not a build form. The observed construction link shape is `GET /?village=<id>&s=build_main&a=buildBuilding&p=<opaque>&build=<slug>`; `build=main` denotes the castle and `build=storage` the warehouse (also observed: `stone`, `wood`, `iron`, `farm`, `hide`, `barracks`). `s` selects the screen; `m` appears as a mode on other screens, while `a` names an action. The exact purpose of `p` is unverified: take it from the current page, never invent it. Inspect **parameter names only** during reconnaissance; never print or persist session-specific values, and never issue an action link without separate authorization. A table headed `Progresso de construção do povoamento` is settlement progress, not proof of an active building queue. Keep write commands disabled until separate permission and post-action verification exist. The resource counters may update client-side while the server-rendered build button remains disabled; after balances become sufficient, reload the read-only build page and verify it still resolves to the authenticated world before treating the button as actionable. A reload can redirect to the lobby even after a valid-looking prior DOM snapshot; stop and request manual re-entry rather than treating the cached page as an active session.

7. For an explicitly authorized upgrade, re-fetch `build_main` just before acting; require the exact current level, enabled button, expected costs, adequate balances/workers and no active build queue. Compare the target link's origin and `village`, `s`, `a=buildBuilding`, `build` fields, taking its opaque `p` only from that fresh page. Submit **once** without automatic redirects or network retries. The live server may return HTTP 302 after an accepted command; the redirect is not proof. Re-fetch the read-only page and require a queue entry for the target (a `.borderlist` containing `cancelar`, with a target `Nível N+1`) and deducted resources. Wait for completion, then verify the actual level and hourly production in `#wood`, `#stone`, `#iron` (`title="... por hora"`, `prod` attribute). Do not count `Nível N + 1` as completed. If a user or another actor queues the same upgrade while you are checking, do not issue a duplicate command; observe its completion instead. If the response or queue is ambiguous, stop rather than re-submit. The live card `.res1/.res2/.res3` mapping was corroborated for observed mine/sawmill upgrades by before/after balances, but recheck it for other screens or worlds.

Keep copied cost tables out of this reference: they are world-dependent data and belong in a source-attributed project catalog or fresh retrieval, not persistent class instructions.
